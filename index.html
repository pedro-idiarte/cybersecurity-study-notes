Understanding IAM, IGA, PAM, SAML and LDAP

Every company needs an answer to three questions: who are you, what are you allowed to touch, and how do we protect the accounts that can touch the most. This guide walks through the pieces that answer them — from the broad discipline down to the specific protocols — and how they fit together.

Start learning
IAM

Identity & Access Management

IAM is the umbrella discipline: creating digital identities, proving people are who they claim to be, and deciding what they're allowed to reach. IGA and PAM are specialized parts of this same picture, not separate worlds.

The core pieces

  • Identity — a record representing a person (or a service) in company systems.
  • Authentication — proving you are who the identity says you are (a password, a key, an app confirmation).
  • Authorization — deciding what an authenticated identity is permitted to do.
  • Access management — the ongoing job of granting, adjusting and revoking that access.
  • Identity lifecycle — everything from the day an identity is created to the day it's retired.

Pedro joins a company

  1. An identity is created for Pedro.
  2. He receives an account.
  3. He's assigned appropriate access.
  4. He authenticates through the identity provider.
  5. He reaches the applications he's authorized for.
  6. When he leaves, his access is revoked.

Key takeaway — IAM is the broad discipline of managing digital identities and the access tied to them.

IGA

Identity Governance & Administration

IGA answers a harder question than "can this person log in?" — it answers what access should this person have, why, who approved it, and when should it end.

What IGA covers

  • Joiner / Mover / Leaver — the lifecycle events that trigger access changes.
  • Access requests & approvals — asking for access, and someone signing off on it.
  • Access reviews & certifications — periodically confirming access is still needed.
  • Provisioning / deprovisioning — automatically granting or removing accounts.
  • Least privilege & audit — keeping access minimal, and proving it on request.

Platforms in this space include SailPoint, Saviynt and One Identity — different products, same job: governing who has access to what.

Maria joins as a developer

Automatically receives:

  • Git repository access
  • Dev environment
  • Jira access

Does not receive:

  • Production DB admin
  • Payroll system

Key takeaway — IGA decides and proves who should have access, and removes it the moment that stops being true.

PAM

Privileged Access Management

Some accounts can do far more damage than a normal login — domain admins, root, database admins, cloud admins. PAM exists to keep those accounts from being a standing risk.

How it's protected

  • Just-in-time access — privileges granted only for the window they're needed.
  • Credential vaulting — privileged passwords stored and rotated automatically, not memorized.
  • Session monitoring — privileged sessions are recorded or watched live.
  • Temporary elevation — access expires on its own instead of lingering.

CyberArk, BeyondTrust and Delinea are common examples of PAM platforms.

An employee needs a production server

  1. Requests privileged access.
  2. Request is approved.
  3. Access is granted temporarily.
  4. The session is monitored.
  5. Privileges are removed once the task is done.

Key takeaway — PAM protects the small set of accounts that could otherwise cause the most damage.

SAML

Security Assertion Markup Language

SAML is a protocol, not a programming language and not an identity provider itself — it's the format two systems use to tell each other "this user is authenticated," commonly powering single sign-on.

Core concepts

  • IdP — authenticates the user.
  • SP — the application the user wants to use.
  • Assertion — the signed statement the IdP hands the SP, saying who the user is.
  • SSO — one login, many applications.

Entra ID, Okta, Ping Identity and Keycloak are common SAML-capable identity providers.

Reaching Salesforce through Okta

"The IdP authenticates the user, and the Service Provider trusts the IdP's assertion."

Key takeaway — SAML lets one trusted login work across many applications, without each one checking passwords itself.

LDAP

Lightweight Directory Access Protocol

LDAP is a protocol for reading and managing directory information — the users, groups and attributes an organization keeps in one place. Active Directory supports LDAP, but the two are not the same thing.

Directory building blocks

  • Entry — one record in the directory, such as a user.
  • DN — the unique path identifying that entry.
  • Attribute — a field on an entry, like an email address.
  • Group — a named collection of entries.

Company directory tree

dc=company,dc=com
  ou=employees
    cn=Pedro
      mail=pedro@company.com

An application can query this tree to look up Pedro's email or group membership.

Key takeaway — LDAP is how systems read and manage directory data — it's a protocol, not a product, and not the same thing as Active Directory.

How it all connects

In a real company these pieces work together rather than replacing one another.

LDAP/Active Directory hold identity data, the IdP authenticates against it via SAML/OIDC, and IAM — with IGA and PAM underneath — governs what happens next.

Comparing the concepts

ConceptMain purposeExample
IAMManage identities and accessEntra ID
IGAGovern identities and accessSailPoint
PAMProtect privileged accessCyberArk
SAMLAuthentication / SSO federationOkta ↔ Salesforce
LDAPAccess directory informationActive Directory

These aren't interchangeable — each solves a different part of the identity problem.

A day in the life of an employee

Pedro joins a technology company. Here's every system that touches his access, in order.

  1. HR creates the employee record.
  2. IGA provisions the identity.
  3. LDAP / Active Directory stores his directory information.
  4. The IdP authenticates Pedro.
  5. SAML provides SSO to enterprise applications.
  6. IAM controls what he can reach.
  7. Pedro requests temporary production access.
  8. PAM grants temporary privileged access, then removes it.
  9. Pedro leaves the company.
  10. IGA triggers deprovisioning — access is revoked.
